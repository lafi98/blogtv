# AI Publisher — keyword → published article

Give the site one crochet keyword and it produces, checks and publishes a complete article. Or queue many
keywords and it publishes **exactly one validated article per day** until the queue is empty.

```
KEYWORD
 → duplicate check in the database, no Claude call yet    ── exact keyword, related keywords, similar titles, queue
                                                              duplicate ⇒ SKIPPED_DUPLICATE, nothing created
 → topic analysis (Claude: intent, format, length, safety) ── overlapping search intent or a planned title that
                                                              duplicates an existing one ⇒ SKIPPED_DUPLICATE
                                                              (before any research or writing)
 → research (Claude + web search; sources recorded)
 → article generation (Claude, structured output: title, body, FAQ, SEO + OG fields, related keywords)
 → reviewer pass (Claude: facts, stitch maths, fabricated/misleading claims, policy)
 → SEO metadata (unique slug, SEO title, meta description, OG title/description, primary + related keywords;
                 canonical URL is automatic: SITE_URL + /blog/<slug>)
 → H1 = article title (rendered by the page); body uses H2 sections and H3 sub-sections
 → internal links (only to PUBLISHED articles; anything else is removed — never broken, never invented)
 → external references (only verified research sources / trusted references; never social networks, marketplaces
                        or link shorteners; at most a few, only where they genuinely help)
 → featured image (original illustration generated by the site; safe fallback image)
 → validation (strict mode)                                ── any error ⇒ DRAFT, not published
 → save + publish/schedule (one database transaction)      ── failure ⇒ nothing saved, keyword not consumed
 → audit log (ai_runs + audit_log)
```

## Using it

**Admin → AI Publisher** (`/admin/topics`):

| Control | What it does |
| --- | --- |
| **Keyword** + **Generate Draft** | Creates the article and saves it as a DRAFT (validation results shown). Nothing is published. |
| **Keyword** + **Generate & Publish** | Publishes only if validation passes. If today's AI publication already happened, the article is SCHEDULED for the next free day instead (the one-per-day limit is never exceeded). |
| **Add Keyword(s)** | Adds keywords to the daily queue (one per line, up to 200 at once). Duplicates of existing articles or queued keywords are refused with an explanation. |
| **Pause / Resume Daily Publishing** | Turns the daily publisher OFF/ON. When OFF, the cron does nothing. |
| Queue actions | Move to top · Remove · Re-queue (for failed/skipped keywords) |

After you click Generate, you're taken to the run page (`/admin/runs/<id>`), which refreshes itself until the
run finishes and then shows: status, Claude result, validation errors and warnings (exact messages), publication
result, links to the article (edit / preview / live) — or, for a duplicate, which existing article covers the topic
and why. Every run is listed in **Admin → AI run log**.

### Duplicate protection

Only real articles count — **published, scheduled or awaiting review**. Unpublished drafts never block a keyword
(a retry simply updates its own earlier draft). A keyword is refused, with no Claude call, when:
- an existing article already targets the exact keyword, or
- the keyword is one of an existing article's related keywords (same search intent), or
- every *specific* word of the keyword (ignoring generic words like "easy", "crochet", "beginners", "pattern", "how to")
  already appears in an existing article's title/slug/primary keyword — e.g. *crochet granny square for beginners* is covered by
  *Classic Granny Square Pattern for Beginners*, or
- most specific words overlap (4+ specific words, 75%+ shared), or the same keyword is already queued.

After the (cheap) topic-analysis call and **before any research or writing**, it is also skipped when Claude judges that an
existing article already answers the search intent, or when the planned article title duplicates an existing title.

The explanation names the existing article and links to it. Pick a more specific angle (e.g. *crochet market tote bag
pattern* instead of *easy crochet bag pattern*).

### Statuses

Runs: `QUEUED → GENERATING → VALIDATING → PUBLISHED | SCHEDULED | DRAFT | FAILED | SKIPPED_DUPLICATE`.
Keywords: `queued`, `generating`, `published` (the only "consumed" state), `scheduled` (reserved; consumed when it
actually goes live), `draft` (Generate Draft mode), `failed` (3 unsuccessful attempts or rejected topic — Re-queue to
retry), `skipped_duplicate`.

## Safety rules (enforced in the database, not the browser)

- **Max 1 AI publication per day** (`MAX_AI_PUBLICATIONS_PER_DAY = 1` in `src/lib/publishing/publisher.ts`). Each
  publishing day has one row in `ai_publication_slots` (primary key = date). A run must claim the day inside an
  `IMMEDIATE` transaction before generating, so repeated or simultaneous cron calls can't publish twice.
- **One run at a time** (`ai_locks`). A second cron call while a run is in progress returns `already_running`
  and does not consume a keyword.
- **Keyword consumed only by a successful publication**, in the same transaction that publishes the article (or, for a
  scheduled article, when it actually goes live). Claude/API errors, validation failures and publication failures leave
  the keyword unconsumed: it goes back to the **end** of the queue so the next keyword gets its turn, and is retried —
  up to 3 attempts, then parked as `failed` for you to look at. A validation failure also keeps the DRAFT (with the exact
  errors) so you can fix and publish it by hand; publishing it from the editor then marks the keyword as used.
- **At most 3 attempts per day** (cost control). Interrupted runs (server restart) are recovered after 45 minutes.
- **Validation (strict mode for AI articles)** must have 0 errors to publish: title, H1 (no second H1 in the body),
  H2/H3 hierarchy (sections start at H2, no skipped levels, at least two H2s), duplicate topic/content, category,
  meta description, slug, featured image + alt text, broken/unpublished internal links, untrusted external links,
  keyword stuffing, fabricated/unsupported/misleading claims,
  readability, required sections (introduction, headings, closing section), dangerous or inappropriate content, ad-click
  encouragement, crochet fact rules (hook sizes, US/UK terms, yarn weights), and reviewer high-severity findings.
- **Article length follows search intent** (short / medium / long chosen during topic analysis). Only genuinely thin pages
  (< 300 words) fail.

## 1. Connect Claude (server-side only)

Set in your host's secret settings (or the git-ignored `.env`), then restart:

```ini
ANTHROPIC_API_KEY=sk-ant-...      # required
AI_MODEL=claude-opus-5-5          # optional (default)
AI_EFFORT=high                    # optional: low | medium | high | xhigh | max
AI_WEB_SEARCH=true                # optional; web search must be enabled for your org in the Anthropic Console
```

The key is read only by `src/lib/publishing/claude.ts` on the server. It is never sent to browsers, never in client
code, and `.env` is git-ignored. If it's missing, the admin shows a clear "Configuration needed" message, the cron
returns `503 {"code":"ANTHROPIC_API_KEY_MISSING"}`, and nothing is consumed.

**Cost:** each article uses 4 Claude requests (analysis, research with up to 5 searches, writing, review). Token usage
per run is on the run page.

## 2. Configure the daily schedule

1. **Admin → Settings → Automation**: Daily publishing **ON**, **Publishing time** (e.g. 09:00), **Time zone**
   (e.g. Europe/London). "Today" and the publishing time are evaluated in that time zone.
2. Set `CRON_SECRET` (≥ 24 random characters) on the server:
   `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`
3. Create **one** scheduled job on your host that calls the endpoint **every 15 minutes** (anything from 5 to 60
   minutes works — the app itself decides when the day's article is due):

```
GET or POST https://YOUR-DOMAIN/api/cron/daily-publish
Authorization: Bearer YOUR_CRON_SECRET
```

The same call also publishes any SCHEDULED articles that are due, so no second job is needed. It returns quickly
(`202 started` while the article is generated in the background on your server, or `200 noop` with the reason:
`daily_publishing_off`, `before_publish_time`, `daily_limit_reached`, `queue_empty`, `already_running`,
`max_attempts_reached`). Missing/wrong secret → `401`; `CRON_SECRET` not set on the server → `503`.

### Host-specific setups

**Linux server / VPS (crontab)** — either call the URL, or run the command in the app folder:

```cron
*/15 * * * * curl -fsS -H "Authorization: Bearer YOUR_CRON_SECRET" https://YOUR-DOMAIN/api/cron/daily-publish > /dev/null
# or, same machine and same data folder as the app:
*/15 * * * * cd /srv/crochet-blog && NODE_ENV=production npm run -s publish:daily >> /var/log/crochet-daily.log 2>&1
```

**systemd timer** (`/etc/systemd/system/crochet-daily.timer` + `.service` with
`ExecStart=/usr/bin/curl -fsS -H "Authorization: Bearer …" https://YOUR-DOMAIN/api/cron/daily-publish`,
`OnCalendar=*:0/15`).

**Render / Railway / Fly.io / other PaaS** — create a scheduled job (cron service) with schedule `*/15 * * * *` and the
command `curl -fsS -H "Authorization: Bearer $CRON_SECRET" https://YOUR-DOMAIN/api/cron/daily-publish`.
Use the HTTP call rather than `npm run publish:daily`: scheduled jobs on these platforms usually run in a separate
container that does not share your web service's database disk.

**cPanel / shared hosting cron** — command:
`curl -fsS -H "Authorization: Bearer YOUR_CRON_SECRET" https://YOUR-DOMAIN/api/cron/daily-publish >/dev/null 2>&1`

**External cron services (cron-job.org, EasyCron, …)** — URL `https://YOUR-DOMAIN/api/cron/daily-publish`, method GET or
POST, custom header `Authorization: Bearer YOUR_CRON_SECRET`, every 15 minutes. (The endpoint answers in under a second,
so short request timeouts are fine.)

**GitHub Actions** (`.github/workflows/daily-publish.yml`; add `CRON_SECRET` and `SITE_URL` as repository secrets):

```yaml
on:
  schedule:
    - cron: '*/15 * * * *'
  workflow_dispatch:
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - run: curl -fsS -H "Authorization: Bearer ${{ secrets.CRON_SECRET }}" "${{ secrets.SITE_URL }}/api/cron/daily-publish"
```

Note: the article is generated **on your server**, so the app must be a long-running Node process (VPS, container or
PaaS web service with a persistent disk). It does not depend on your browser or your computer being on.

**Check it works:** Admin → Dashboard → *Daily AI Publisher* shows "Last scheduler call" with the time and result of the
most recent call.

## 3. Daily routine (automatic mode)

1. Add your keywords (e.g. 30) in Admin → AI Publisher.
2. Turn Daily Publishing ON.
3. Each day, at the first scheduler call after your publishing time: next keyword → duplicate check → generate →
   validate → publish → keyword marked published → audit log. If anything fails, nothing is published and the keyword
   is not consumed; the dashboard shows the last error.
4. When the queue is empty, the scheduler does nothing.

## Testing without an API key

- `npm test` — 18 automated tests (all 15 required scenarios plus time-zone, scheduling and attempt-limit checks) using a
  simulated Claude client and a throwaway database.
- Local click-through: run `AI_SIMULATE=true npm run dev` (development only; refused in production builds). The simulated
  client returns a sample "easy crochet flower" article without calling the network.

## Editing the editorial voice

`src/lib/publishing/prompts.ts` holds the analyst, writer and reviewer instructions. Keep the accuracy and honesty rules
(no invented experiences, statistics, reviews or expertise; no health or income claims; only verified links) — they keep
automated articles helpful and within Google's publisher policies.
